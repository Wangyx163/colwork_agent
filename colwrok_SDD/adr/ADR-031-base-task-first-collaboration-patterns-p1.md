# ADR-031｜先闭环基础任务，协作结构模板进入 P1

状态：ACCEPTED；P1 最小规则于 2026-08-07 冻结  
日期：2026-08-06  
影响：明确 N01、N02、N13 与 MVP Profile 中多阶段协作结构的优先级

## 背景

真实会议可能出现“多人分别产出 → 一人汇总 → 多人投票/反馈 → 一人定稿”的链路。它不能准确降格为一个普通 ActionItem，也不应把所有参与者都写成同一任务的共同 owner。P0 先把单负责人基础任务的抽取、复核、版本化派发/回应、承诺、追踪、提交、验收、结果处理、终稿和恢复闭环稳定，再用 P1 最小关系补充该特殊场景。

## 决策

1. P0 只执行相互独立的基础 ActionItem；会议明确协作者不形成任务依赖或共同 owner。协作者对原 ActionItem 的贡献权限与同一版本链规则由 ADR-034 定义。
2. P1 不实现三套通用模板，只保留当前会议需要的“多人分别收集问题 → Agent 整理候选 → 指定成员评分 → 一名负责人定稿”。它是基础 ActionItem、依赖边和参与输入的组合，不建立复合任务实体。
3. 只允许 SYSTEM 从会议组织人的原文提出结构建议，由 COORDINATOR 在定稿任务首次派发前复核上游任务、最终负责人、投票人、保留数和原文依据。
4. 协作结构模板是抽取与展开规则，不建立独立工作流引擎、第二套流程状态、LangGraph 或通用 DSL。
5. 文档编号遵循现有模块：抽取规则补充在 N01，推进规则补充在 N02，UI 补充在 N13；不使用 `N02.5`、`N0.25` 等小数编号。若未来确需独立模块，必须新增下一个完整 `Nxx` 并更新索引、接口、状态和验收计划。

## P1 最小边界

- 同一 Episode 内、无环、显式来源；上游输入只引用人工验收后的 `accepted_version_id` 并保留 lineage。
- 上游全部验收后，最终负责人才能生成 ballot 草稿；`bailian` 模式只用 `qwen-plus + temperature=0 + question-ballot-draft.v1` 做语义抽取/去重，状态、权限、来源校验和计分仍是确定性规则。模型契约修复一次后仍失败时，仅在规则抽取至少得到两个有来源候选时降级。
- ballot 草稿可由最终负责人删选和修改文字；正式发布后锁定。每位指定投票人必须对全部候选给 1–5 整数分，首次提交后锁定，不允许改票；全部指定投票完成前不得提交定稿。P1 不做缺席、弃权、提前关票或 quorum DSL。
- 得分排序为总分降序、平均分降序、`option_id` 升序；投票结果只解锁最终负责人普通提交，不替代人工验收。
- 上游有效版本变化时，旧 ballot、投票和定稿结果失效，下游回到 TRACKING 并绑定新 lineage 后重开。
- 不实现跨 Episode 依赖、条件分支、任意工作流编排、多 owner 或通用 Skill Router。

## 结果

- P0 工期继续集中在基础任务闭环，不被特殊场景拖住。
- P1 有明确落点和验收边界，不会重新讨论是否引入通用工作流框架。
- 特殊场景不会被错误建模为默认协作者或一个不可追踪的复合任务。
