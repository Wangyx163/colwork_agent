# ADR-036｜召回优先的抽取与复核提示

状态：ACCEPTED  
日期：2026-08-11  
影响：修订 N01、领域模型 DATA-AI-001、API-EXTRACT-001、API-REVIEW-001 与 SIG-EXTRACT-001；保留 ADR-028/ADR-035 的“单 ActionItem 主流程、不建立第二套候选任务实体”边界

## 背景

现有抽取链在一次模型调用中同时要求判断行动项、补齐结构字段、选择单行引文并排除不确定语料。任一候选 schema 或引用失败可能扩大为片段乃至整场会议失败；证据修复又只允许删除、不得新增。这个设计偏向精确率，与会议 Agent “宁愿多召、错召，也要尽量避免少召、漏召”的产品目标不一致。

同时，会议行动经常分散在“提议—补充—确认”多个发言中。固定取 3–5 个上下文单元没有稳定语义依据：短确认可能需要向前寻找提议，长发言自身已经足够，固定窗口既可能不足也可能引入无关话题。

## 决策

1. 抽取内部拆成“候选发现”和“结构整理”两种责任，但产品只呈现一个 COORDINATOR 复核表面，不向用户暴露两套流程或两套任务状态。
2. 候选发现使用**一套统一的宽召回 Prompt**扫描带稳定 `unit_id` 的全文片段，并与确定性词法/结构规则的结果取并集。当前不采用按任务/承诺拆成两套 Prompt；只有后续同集消融证明某类漏召无法由统一 Prompt 修复时，才另立 ADR 增加第二语义扫描。`选择/通过/同意/就按/采用/改成/不再` 等多义决策词继续参与候选发现，但标记为弱信号，不得仅凭单词命中直接生成 `draft_item`。
3. 第一阶段只定位可能相关的 `unit_id`、候选类型提示和触发来源，不要求模型生成 title、deliverable、owner、deadline 或自由文本 `source_quote`。引用正文、时间戳与字符范围由系统根据 unit 确定性回填。
4. 召回扫描使用带中央责任区的重叠滑动窗口：`left_context + emit_zone + right_context`。模型读取整个窗口，Prompt 要求只为 `emit_zone` 中的 anchor 产生候选；所有 unit 必须恰好一次落入某个 emit zone，左右 context budget 原则上各占窗口至少四分之一，首尾窗口可把空余预算让给另一侧。窗口按完整 unit 边界生成。若模型仍返回全部位于本窗可见 context 的合法 anchor，召回优先校验不得直接删除：标记为 `VISIBLE_CONTEXT_ANCHOR_RECOVERED` 后进入全局并集，与其责任 emit 窗口产出的同 anchor/type 候选合并；未知或不可见 anchor 仍逐候选隔离。恢复候选不改变 emit coverage 账本，也不得伪装成责任窗口输出。当前 `emit-owned-char-window.v2` 冻结为 `800 + 1600 + 800` 字符；这不是语义必需常数，而是 82 场确定性窗口账本下对调用碎片度与局部上下文的折中：旧 `1000+2000+1000` 为 1063 窗/约 391 万渲染字符，v2 为 1320 窗/约 392 万字符，`600+1200+600` 增至 1761 窗但总字符仍约 394 万，未获得总输入收益。
5. 滑动窗口只保证每个 anchor 在有界左右语境中被判断，不声称覆盖任意距离的上文。候选发现后，证据整理必须回到全局逐字稿按 unit id 重建上下文，不受发现它的 chunk 边界限制。发现模型返回的 `support_unit_ids` 只表示解释 anchor 必需的直接确认或指代补全，不承担整段证据打包；不得把同话题的复述、理由和一般上下文整段列为 support。系统按版本化字符预算保留离 anchor 最近的合法 support，未知或超预算 support 只记录并裁剪，不得连带删除合法 anchor 候选。unit id 只允许做无歧义格式归一化（例如把 `u14.0` 补零为窗口中确实存在的 `u000014.000`）；归一化后不存在或不可见时不得猜测。更完整的证据仍由后续全局自适应扩展负责。
6. 结构整理采用上下文充分性判断，不使用固定 3–5 units：
   - TASK 至少需要“要发生的动作 + 对象或结果”；owner 与时间允许缺失。
   - COMMITMENT/DECISION 至少需要“未来事件或决定内容 + 明确接受、时间或条件之一”。
   - 单个候选若只含一个独立语义事实，或含短确认、指代、省略、单独时间等不自足表达，先加入前后各一个 unit；仍不足时按同一话题继续扩展，直到语义充分、遇到话题边界或达到版本化字符预算。达到预算仍不足不得删除。
7. 上下文扩展按需而非一次塞入固定数量：先扩前后各一 unit；短确认和指代优先向前寻找被确认/指代内容，时间或结果补充则同时检查前后；每轮扩展后重做充分性判断。同一候选的 anchor 与合法 support 之间若没有话题边界，且补齐完整区间后仍在同一硬字符预算内，系统必须把中间 unit 作为 `LINKED_EVIDENCE_BRIDGE` 保留，不能只拼接两个端点而丢掉中间的频率、条件或确认细节。话题边界是停止提示而非硬删除条件，达到安全预算仍不足时保留当前完整 context trace。`嗯/好/行/收到` 等短确认不独立产生任务候选或卡片：系统在话题边界和版本化字符预算内向前寻找最近的动作/决定，把动作句设为 anchor、确认句只设为 support；找不到被确认内容时只能保留为 hint。
8. 语义充分的结果进入 `draft_items`，导入后直接成为 `PENDING_CONFIRMATION` ActionItem。draft 充分性必须与 anchor 绑定：邻近上下文可补对象、结果、时间、条件或接受信息，但不得把无关邻句中的动作借给仅有指派词的 anchor。弱决策信号需要动作、时间、条件或独立确认等第二证据才能升级；否则与其他扩展后仍不足的结果一起进入抽取 artifact 的 `review_hints`，保留 evidence/context unit、触发来源和不足原因。hint 不是 ActionItemCandidate 领域实体，也没有独立状态机。
9. `draft_items` 与 `review_hints` 在同一个负责人复核页面呈现。COORDINATOR 可从 hint 添加任务、直接手工添加任务或忽略 hint；只有人工添加后才创建 ActionItem。
10. 校验和修复必须逐候选隔离。一个候选字段、锚点或模型 JSON 条目失败不得删除同批其他候选，也不得把整场会议解释为空。确定性 draft 充分性已通过时，结构模型失败或漏项保留可追溯的 fallback draft；充分性未通过时始终进入 `review_hint`，模型不得把弱证据强行升级。
11. 每场抽取必须分别记录 `emit_zone_coverage` 与上下文读取范围，以及候选来源、上下文扩展、逐候选校验结果和降级原因。只要规则补网完成但模型 emit zone 覆盖不完整，运行状态为 `DEGRADED`，不得伪装为 `SUCCEEDED`。
12. 召回评测的主指标是候选召回与第一阶段命中项的后处理存活率。原始候选数是工作量，句级 TP/FP/FN 必须先按引用句去重，二者不得混算。评测同时分别报告 raw anchor、显式 anchor+support、draft/hint 路由后 evidence 的金标覆盖；support/evidence 不是预测正例，只能报告 recall coverage，不能伪造 precision/F1。候选数之外必须报告 anchor/support unit 引用量与 support 裁剪量，防止通过枚举整段 support 制造虚假高召回。抽取失败会议按空预测计入全部 FN；AMC-A 没有条目级金标时 item-level 指标返回合法 N/A，不得输出误导性的 0。AMC-A 零正例会议只能称为“零标注会议”，不能在没有产品口径人工标注时宣称为真正的零行动项会议或把全部输出定性为产品误报。
13. Review Load 不作为召回阶段 Gate，也不用于删除或隐藏候选。若未来需要衡量人工成本，应作为真实负责人复核后的非阻断 SIGNAL 单独设计。
14. 评测运行按 manifest 固定 meeting IDs、数据/unitization/窗口/Prompt/候选归一化/规则/证据/模型版本；provider 窗口响应 checkpoint 至少由 Prompt、模型和窗口内容共同定址，meeting 结果 checkpoint 还必须包含全部下游策略版本。按 meeting/stage/window 原子写检查点和单场分数，支持断点续跑与零模型调用重算。报告必须同时区分 `SUCCEEDED | DEGRADED | FAILED`，失败会议不得从聚合分母移除。

## 验证记录（2026-08-12）

- 固定 manifest 为 AMC-A `except_TS_test1` 的 15 场：共同对照 8 场，加 7 场有正例会议的长度分位样本；共 7,398 句、49 条句级金标、9 场有正例、6 场零标注。报告为 `evaluation_runs/recall-selected-v23-pilot15-final-v2.json`。
- 使用 `meeting-recall-first.v2.3`、`emit-owned-char-window.v2 (800+1600+800)`、候选归一化 v4、规则词表 v3、证据策略 v3。227/227 个百炼窗口成功；实际用量为 prompt 581,955、completion 71,459、total 653,414 tokens。
- 模型与规则并集的严格 raw-anchor 句级结果为 TP=39、FP=1,181、FN=10，P=0.0320、R=0.7959、F1=0.0615。显式 anchor+support 覆盖 46/49（0.9388）；路由后 evidence 覆盖 49/49（1.0）。后者包含 2,379 个 `LINKED_EVIDENCE_BRIDGE` unit 引用，必须作为证据整理覆盖解释，不能冒充模型句级分类能力。
- 15 场共 1,049 个 raw candidates、251 个 draft_items、780 个 review_hints；平均每场约 69.9 raw、16.7 draft、52.0 hint。6 场零标注切片平均仍有 11.5 draft 与 33.5 hint，说明当前瓶颈已从静默漏召转向负责人复核负载与候选分组，不能宣称“空会议干净”。
- 14 场 `SUCCEEDED`，1 场因模型候选数组中 2 个非对象元素而 `DEGRADED`，无 `FAILED`。41 个欠补零的 unit id 被无歧义归一化；108 个可见 context anchor 被恢复，48 个与责任窗口候选合并；未知/不可见引用仍隔离。
- 本次按产品决定直接选择 `800+1600+800` 后验证，不是同 Prompt 下的完整窗口最优性消融，因而只能说明该配置在此 manifest 上可用，不能宣称优于所有 `left/emit/right` 组合。多步骤投票/审批仍需要另行实现跨窗口 event/thread 拼接并专项验证。

## 结果

- 模型仍可能语义漏召，但系统不再把已经发现的候选因字段不全、单行证据不足或结构整理失败而静默删除。
- 不确定语料有明确容错出口，由会议负责人决定是否创建任务；领域主线仍只有 ActionItem，不引入候选任务表。
- 一个统一 Prompt 与规则补网先建立可验证基线，避免在没有消融证据时支付双 Prompt 成本和重复候选复杂度。
- 中央责任区让每个 unit 都在有左右语境的位置被判断；重叠上下文提供有界的局部完整性，后续全局证据扩展处理更远的补充信息。
- 多步骤投票、审批等流程不得依赖继续放大单个发现窗口来获得完整性；窗口只发现提案、投票、确认或结果 anchor，未来扩展通过有序 unit/event/thread 关联在窗口间拼接同一流程，并保留每一步原始证据。
- 上下文大小由语义充分性和话题边界决定，字符预算只作安全上限，不充当语义判断；系统只能保证版本化预算内的覆盖与不静默丢弃，不能宣称理解任意距离的隐含指代。
- AMC-A 可继续用于句级候选召回，但产品是否“该让负责人看到”仍需真实会议人工标注验证。
