# N15｜单任务协作报告与协作说明书（Collaboration Memory）

版本：2.0（词表 v2，A/B 两组）
变更依据：ADR-030、ADR-035，以及 2026-08-07 的词表重设计

## P0 职责

### N15-001｜触发与输入

- 仅在 ActionItem 人工验收为 ACCEPTED 后触发；输入绑定 `action_item_id + accepted_version_id`。
- 输入只包含结构化业务事实：承诺修订、有效信号、求助、提交版本、退回反馈、验收结果及可见性标记。
- 不从页面在线、草稿、未发送内容或其他任务私聊推断协作特征。
- 验证：AUTO-N15-001、AUTO-N15-002。

### N15-002｜任务协作报告

- 报告是 version-bound 派生快照，不建立新的主流程实体。
- 至少包含：任务定义、负责人、记录到的协作者及来源、两类日期、承诺变化、各贡献者状态、带真实提交人的交付版本、求助与反馈摘要、最终结果引用、来源事件 ID。
- 报告生成失败不得回滚已验收结果；失败必须可见、可重试并记录原因。
- 验证：AUTO-N15-003、AUTO-N15-004。

### N15-003｜说明书词条（词表 v2）

产品命名统一为**我的协作说明书**；同事侧呈现为「和某某协作时可以注意」，不使用"记忆""画像"这类第三人称措辞。参照形态是 Personal User Manual / How to Work With Me。这个框架转换是有意的：前者被动、有威胁感，后者主动、有掌控感。

#### 为什么用受控词表而不是自由文本

这是图书馆学意义上的 controlled vocabulary（MeSH、Dublin Core 同类）。四个需求缺一不可，而自由文本四个都做不到：

| 需求 | 自由文本为什么失败 |
|---|---|
| 跨会议聚合（接飞书后必须） | 「我喜欢先看背景」和「需要上下文」是同一件事，机器不知道 |
| 同 topic 替换 | 只有封闭取值才能定义什么叫"替换" |
| 跨人展示 | 自由文本会带出具体项目、具体人、具体冲突 |
| 版本化 | lexicon_version 才能证明一条词条当时是什么意思 |

#### 词条的两条构成规则

**其一，观察而非评价**（非暴力沟通）。词条描述工作偏好，永不描述人。可执行检验是**反向性**：

> 把同一 topic 下任意两个取值互换，如果读起来是"更差"而不只是"不同"，这组词条非法。

「先结论后依据」↔「先背景后结论」合法，都是合理的人；「响应快」↔「响应慢」非法，反向是贬义。

`assert_lexicon_is_reversible()` 强制其结构前提：每个 topic 至少两个取值、取值必须第一人称、不得包含"不/少/慢/差/弱/缺/懒/拖"、每条必须给出同事可执行的提示。语义反向性仍需人工评审，但这个函数保证评审有意义。

**其二，自我披露而非反馈**（乔哈里窗）。确认一条词条等于把它从**隐藏区**移到**开放区**，这个移动**只能由本人发起**。由他人发起的属于**盲区**操作（feedback），是完全不同的权限模型和心理契约。系统可以"注意到"一个候选，永远不能"断言"一个候选。这是 PRIVATE_DRAFT 到 CONFIRMED 流程的理论依据。

#### A/B 两组

| 组 | origin | 谁作者 | topic |
|---|---|---|---|
| A 我怎么工作 | SYSTEM_OBSERVED | 系统从审计事实提出候选，本人确认 | DELIVERY_RHYTHM 交付节奏、PROGRESS_SIGNAL 进展同步、HELP_SEEKING 求助习惯 |
| B 我希望别人怎么配合 | SELF_DECLARED | 本人直接填写，无 draft 阶段 | BRIEF_DETAIL 需要多少背景、FEEDBACK_STYLE 希望怎么收到反馈、SYNC_PREFERENCE 偏好的沟通方式 |

分组理由：

1. **A 组是系统的能力**——能从审计事实提出候选，这是 Agent 的价值，也是和"填问卷"的本质区别。
2. **B 组是本人的权利**——系统不该推断"你想要什么样的反馈"，那是猜心思；而同事最需要知道的恰恰是 B 组。
3. **解决冷启动**——新人没有任何任务历史，A 组必然为空；B 组让他第一天就有一份说明书。
4. **结构成本极低**——共用同一张 collaboration_memories 表，只增加 origin 一列，不新增实体。

服务端拒绝对 A 组 topic 调用 `declare_collaboration_memory`，也拒绝把 B 组 topic 作为观察候选提出。

#### 候选提出规则

- **排除返工**：只统计 review_status 不是 REJECTED 的版本。被退回后重交是**任务的属性**，不是人的偏好——这是旧规则最主要的误判来源。
- **如实报告观察广度**：distinct_action_item_count 随候选存储，页面显示「仅在 1 个任务中观察到」或「在 N 个任务中观察到」。
  - 曾考虑把"≥2 个任务"作为**提出门槛**，评估后否决：一次会议 3–5 个任务、每人往往只有一个，设门槛会让候选几乎永远不出现。返工排除已经精确解决了误判，广度作为**信息**呈现即可。
- **三选项平等呈现**（关键）：UI 不得是「系统认为你是 X，[确认]/[拒绝]」。必须平等列出同 topic 全部取值，只标注系统观察到哪一条。只给一个选项点确认，会让说明书退化成系统的自我实现预言。

#### 趣味化边界

> 趣味化可以作用于**呈现**，绝不能作用于**分类学**。

| 可以 | 不可以 |
|---|---|
| 卡片视觉、图标、配色 | 稀有度 / 等级 |
| 第一人称口语措辞 | 星级 / 进度条 / 完成度 |
| 「我的协作说明书」这类命名 | 排行榜 / 团队对比 |
| 每条配一句"同事该怎么做" | 徽章数量对他人可见 |
| 确认时的轻量动效 | **用可爱标签替代准确表达** |

最后一行是最容易踩的失败模式：「细节控」「急性子」「社恐」「夜猫子」读起来有趣，但它们是评价不是观察，会激活刻板印象，同时违反本节第一条构成规则和"明确不做评价性人格标签"。

#### 兼容

v1 的 INFORMATION_STYLE / DELIVERY_STYLE / UPDATE_STYLE / ASSISTANCE_STYLE 通过 LEGACY_TOPIC_ALIASES 与 LEGACY_CODE_ALIASES 继续解析，已确认条目在升级后仍可读。INFORMATION_STYLE 在 v1 是死维度（没有任何证据规则会提出它），v2 归入 B 组 BRIEF_DETAIL 由本人填写。

- 验证：AUTO-N15-005 至 AUTO-N15-007，以及 tests/test_memory_lexicon_v2.py。

### N15-004｜可见性与使用

- 本人可查看候选及已确认词条，并执行确认、同 topic 预制词条替换或拒绝。
- COORDINATOR 只可查看本次任务中的事实证据，不可浏览他人的完整说明书。
- 当前有效协作关系可读取 CONFIRMED 词条的最小可操作提示，不读取 evidence_refs、历史版本或评价字段；产品不提供"展示偏好"开关，确认词条即表示允许在当前协作关系中按固定策略最小使用。
- SYSTEM 只有在明确 purpose=MEMORY_PROPOSAL 或 COLLABORATION_HINT 时读取相应字段；说明书不得参与身份认证、授权、验收结论或惩罚性升级。
- B 组允许不填，且**不显示任何缺失提示**——一旦有"完成度"就变成隐性 KPI。
- 验证：AUTO-N15-008、AUTO-N15-009。

### N15-005｜生命周期

- 状态：PRIVATE_DRAFT | CONFIRMED | REJECTED | SUPERSEDED。
- 同一 actor、topic 的新确认值使旧值进入 SUPERSEDED；替换必须保留来源与版本历史。
- 不把单次行为强行合并为长期结论；无足够证据时不创建候选。
- 验证：AUTO-N15-010、AUTO-N15-011。

## P1（已完成，待真人 UI 验收）

- CONFIRMED 词条已接入 COLLABORATION_HINT Context Builder，供 Agent 调整对本人的协作方式。
- 向当前有效协作者共享最小提示；协作关系结束后停止新的跨人读取。

### 跨会议聚合口径（接飞书前提，现在定）

1. CONFIRMED **跨 Episode 有效**，不是每次会议重新确认——否则没人会填。
2. A 组跨 Episode 累积证据，但观察值变化时**不自动改**，只提示"最近 N 个任务的观察和你确认的不同，要更新吗"。
3. 展示给同事时**不带 Episode 来源**，否则"他在 X 项目里是这样"会变成翻旧账。
4. 本人随时可改；对同事只呈现当前值，不呈现历史（对本人保留）。
5. **不做自动衰减**。改为"超过 N 个月未复核时对同事标注'较早确认'"。自动衰减等于系统偷偷改你的说明书。
