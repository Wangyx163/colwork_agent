# Architecture and Responsibility Boundaries

## 一句话架构

一个可恢复的 Agent Worker 从数据库读取当前事实，调用模型完成受约束的语义工作，再通过领域服务、人工 Gate 和 Outbox 推进多人会议任务。

## 为什么不是纯 LLM Agent

会议协作同时包含两类问题：

- 概率性语义：一句话是否构成行动、跨句信息是否属于同一任务、交付内容如何组织。
- 确定性业务：谁有权限、任务处于什么状态、哪个版本有效、消息是否已经发过、终稿能否发布。

前一类交给模型提议，后一类必须由代码和数据库控制。模型输出无论多可信，都不能直接推进任务状态。

## 主要部件

| 部件 | 职责 |
|---|---|
| `CoordinationService` | 权限、状态迁移、版本、审批和审计事务边界 |
| `AgentWorker` | 从数据库恢复待处理步骤，执行模型或规则处理并写回结果 |
| `Outbox` | 将领域变化转换为可重试、幂等的外部效应 |
| `MockIM / FeishuIM` | 共用一份消息适配器契约，分别支持确定性测试和飞书运行 |
| SQLite / PostgreSQL | 保存领域事实；两个后端共享同一套业务语义 |
| 百炼适配器 | 行动项召回、成果处理、终稿整理和跨会议语义提议 |
| Web Workbench | 负责人和执行成员完成所有人工决策 |
| Observatory | 展示Context、Token、人工Gate、Effect、Audit和lineage |

## 五个关键边界

1. 参会名单是授权边界，系统不从逐字稿猜测参会人。
2. 模型不决定身份、权限、状态、审批、催办等级和版本指针。
3. 领域状态、AuditEvent和Outbox在同一事务中提交。
4. 所有外部可见动作使用稳定EffectId；恢复重试不能产生第二条消息。
5. 终稿只引用人工验收后的最新有效版本，并保留字段来源。

## 为什么是模块化单体

当前目标是证明一个真实的长程协作闭环，而不是展示微服务数量。网页与Worker分进程运行，数据库承担共享状态；领域逻辑仍保留在一个模块化代码库中。这减少了分布式协调成本，同时保留了未来拆分外部适配器和Worker的边界。
