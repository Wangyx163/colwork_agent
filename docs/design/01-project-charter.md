# 多同事会议行动项协作 Agent｜项目立项书

版本：1.4  
日期：2026-08-06  
变更依据：ADR-024、ADR-026、ADR-030

## 1. 项目定义

### 1.1 一句话定义

一个从会议转写中识别并落责行动项、同时协调 3–5 名同事确认承诺和提交交付物、处理催办返工与版本变化，最后把成果收齐汇总给负责人审批的办公协作 Agent。

### 1.2 目标用户

- 主要用户：需要收齐多人材料并对最终结果负责的运营、PM、行政或项目负责人。
- 参与用户：承担具体行动项的 3–5 名同事。
- 后续条件用户：直属上级和未参会团队成员不进入 P0，待飞书身份/组织边界明确后再按 P1/P2 接入。
- 详细组织、用户和权限分层见 `12-mvp-priority-profile.md`。

### 1.3 项目目标

1. 将会议中的责任描述转换为由会议负责人复核、版本化派发并由执行成员逐人回应的 ActionItem。
2. 将同事的交付内容与承诺时间外置为结构化、可修订、可查询的事实。
3. 跨 3–5 个模拟工作日同时推动多个行动项，用事件信号、低成本异常询问和参会者求助推进交付。
4. 接收结构化交付物，处理不合格返工与版本翻新，禁止终稿混入旧版本。
5. 将所有 required ActionItem 的最新有效成果聚合为终稿，经人工审批后归档。
6. 用少量 GATE 验证闭环、权限、版本和恢复正确性，并用流程、效果、单点 SIGNAL 解释任务卡点与协调质量。

### 1.4 MVP 场景

一个 Episode 输入一份会议转写和参会名单，包含 3–5 条行动项。Agent 抽取 ActionItem，会议负责人复核并派发给一名主负责人和必要协作者；当前版本全部成员接受后，各任务独立推进和提交。系统通过 VirtualClock 推进多个行动项，执行 L0–L2 异常询问、参会者求助、单任务成果处理和人工验收，最后聚合终稿并请求放行。

### 1.5 当前范围排除

- 真实企微、钉钉或飞书接入；
- 会议语音转写与会议纪要生成；
- 多 Episode 并发；
- 多 Agent 架构、RAG 与多模态；
- 学术假设、消融、敏感性、帕累托、数据集泛化与 pass^k 结论；
- 多任务评测平台。该能力列为 P2，不提前泛化办公领域实体。

## 2. 产品成功标准

P0 成功不是“跑出一份研究报告”，而是完成一次可信的多人协作闭环：

1. 4 个 ActionItem 被版本化派发给 3 名参会执行人并逐人回应，其中一人负责两项，用于验证跨任务预算；
2. 当前承诺均有来源和修订历史；
3. Agent 根据事件信号与时间窗口执行 L1/L2，且不把刷新、已读或页面停留当作进展；
4. 至少覆盖已读不回、版本翻新和劣质交付；
5. 崩溃恢复后重复外发数为 0；
6. 终稿旧版本混入字段数为 0，lineage 完整；
7. 所有 required ActionItem 归档；
8. 每名同事的触达次数可重算。

## 3. 规范体系

### 3.1 优先级

`02-constitution.md` ＞ 已接受 ADR ＞ `12-mvp-priority-profile.md` ＞ `04-system-sdd.md` ＞模块 spec ＞实现计划＞ README 与演示材料。

发生范围或工期冲突时，必须按“多同事业务闭环 ＞ 高风险副作用与数据正确性 ＞ 产品级可重算评测 ＞ UI 完整度 ＞ 可选扩展”排序。

### 3.2 规范词汇

- **MUST / MUST NOT**：P0 验收必须满足或明确禁止。
- **SHOULD**：默认遵守，偏离需记录理由。
- **MAY**：可选。
- **P0–P3**：按 `12-mvp-priority-profile.md` 定义当前与后续优先级。

### 3.3 变更治理

修改 Constitution、冻结的系统级 SDD、指标契约或 P0 边界必须追加 ADR。低优先级文档不得绕过上游决策重新引入已删除范围。

## 4. 角色与访问边界

| 角色 | 可读 | 可写 / 可触发 |
|---|---|---|
| COORDINATOR（会议负责人） | 本 Episode 管理视图、验收辅助包、终稿和指标摘要 | 复核/派发、团队日期、交付验收、FINAL_RELEASE、取消 Episode |
| 协调 Agent / SYSTEM | 按 purpose 裁剪的领域事实和消息 | 经 Outbox 外发、提交规则允许的领域状态转换 |
| PARTICIPANT（参会者） | 本人负责/协作任务、同任务成员关系和会议聚合进度 | 回应派发、修订本人的个人承诺、快捷回应、向参会者求助、提交交付版本 |
| 同事模拟器 | 寻址给 actor 的消息、VirtualClock、自身脚本状态 | 以固定 actor 身份回复和提交 |
| Harness | 场景配置、领域表、AuditEvent、mock IM 投递记录 | 驱动时间、注入 P0 故障、计算分层验收指标 |

硬性边界：

- 模拟器不得读取 Agent 领域状态、策略参数或其他 actor 消息。
- mock IM 必须强制发送者身份。
- LLM 不得决定是否触达、触达等级、预算或审批。
- Agent 不得替参会者接受/退回派发或作出个人承诺、替会议负责人验收，或绕过审批执行终稿发布。

## 5. 业务链与模块

业务链：

`会议转写/参会名单 → 负责人复核/版本化派发 → 成员逐人接受或整轮退回重派 → 个人承诺 → 信号/询问/求助 → 单任务提交/处理/验收 → 结果/协作报告/Memory → 成果汇总 → FINAL_RELEASE → 归档`

| 模块 | P0 职责 |
|---|---|
| N01 Intake + Confirmation | 转写抽取候选并由负责人确认、修订或拒绝 |
| N02 Commitment Ledger | 保存当前承诺、来源和不可变修订历史 |
| N03 IM Adapter | mock IM、身份强制、收发顺序与幂等 |
| N04 Intervention Policy | 信号、L0–L2 确定性询问、预算和参会者求助 |
| N05 Approval Gate | 终稿人工审批 |
| N06 Version Validation | 单任务分层接收、PDF/text 处理、人工验收与结果冻结 |
| N07/N08 Aggregate + Archive | 按最新有效版本生成带 lineage 的终稿并归档 |
| N09 Persistence + Outbox | 领域状态、AuditEvent 和 Outbox 同事务；外发恢复 |
| N10 Context | 可信 Principal、purpose 与最小字段上下文 |
| N11 Simulator | 3 名参会者、4 个核心行为、模板话术 |
| N12 Harness | 单场景驱动、一个故障点和分层指标报告 |
| N13 UI | 角色页面、团队工期、提交/验收、FINAL_RELEASE 与诊断摘要 |
| N14 VirtualClock | 离散时间推进、到期触发和模拟日预算 |
| N15 Collaboration Memory | 单任务协作报告、预制 Memory 候选与最小协作提示 |

N01–N15 是模块化单体中的逻辑职责，不要求拆成独立服务。

## 6. 数据与运行时权威

### 6.1 领域表

- PostgreSQL 领域表是当前业务事实的唯一权威源。
- ActionItem、CommitmentRevision、ArtifactVersion、Approval、Intervention 与 FinalDeliverable 必须持久化。
- 进程重启后，Orchestrator 从领域表、Outbox 和 VirtualClock 推导下一步。

### 6.2 AuditEvent

- AuditEvent 是 append-only 审计与评测轨迹。
- 领域变更、AuditEvent 与对应 OutboxEntry 在同一事务提交。
- AuditEvent 不承担 Event Sourcing、投影重建或领域分歧裁决。

### 6.3 Outbox

- Agent 的所有外部可见动作必须经 Outbox。
- mock IM 对稳定 effect_id 去重并返回既有回执。
- Dispatcher 允许重试；同一 effect_id 最多产生一条外部可见消息。
- P0 只强制“外部接受后、本地确认前崩溃”这一恢复场景。

### 6.4 单一恢复语义

P0 不引入第二套工作流状态或流程位置记录。LLM 只作为抽取与可选话术能力，不承担流程状态或恢复位置。

## 7. 多同事推进策略

- 未确认超过 confirmation_timeout：L1 确认提醒。
- 距离个人承诺尚远：L0 内部观察，不因沉默打扰。
- 已进入检查窗口且超过 silence_window：L1 私聊结构化快捷询问。
- 已逾期且 L1 后仍无有效信号：L2；P0 不通知直属上级。
- 存在未解决求助时跟踪求助，不发送泛化进展询问；求助对象仅限本次参会者。
- 最新交付校验或验收失败：返回可操作原因，等待新 ArtifactVersion。
- 每名负责人有简单每日触达上限；跨行动项消息合并为 P1。

## 8. 分层验收指标

| 层级 | 内容 | 是否阻塞验收 |
|---|---|---|
| GATE | 完整闭环、零重复外发、版本/lineage 正确、审批与预算无绕过、关键恢复成功 | 任一失败即 P0 不通过 |
| FLOW SIGNAL | 行动项漏斗、按承诺有效交付率、关键阶段耗时 | 只解释流程，不单独判失败 |
| EFFECT SIGNAL | 每人触达、触达后进展、升级摘要 | 只解释协调效果，不声称因果 |
| NODE SIGNAL | 提取、版本校验/返工、审批、Outbox 健康度 | 用于定位单点问题 |

全部指标必须能依据领域表、AuditEvent、mock IM、Outbox 与冻结场景配置重新计算；详细口径见 `contracts/metrics-contracts.md`。

## 9. 10–15 日排期

估算前提：1 名熟悉 Python/PostgreSQL 的全职开发者配合 AI 编码；使用固定转写 fixture、mock IM、服务端最小页面，需求范围在 D1 后冻结。若缺少该经验或同时建设真实平台接入，10–15 日不成立。

| 阶段 | 内容 | 出口条件 |
|---|---|---|
| D1 | 冻结 P0、schema、角色权限、主场景 fixture | Profile、ADR、schema 一致 |
| D2–3 | N03/N14 骨架；3 名负责人、4 个 ActionItem、VirtualClock | 多同事消息和时间推进跑通 |
| D4–5 | N01/N02；候选、确认、修订、承诺 | 四项任务均可进入 TRACKING |
| D6–7 | N04；信号、L0–L2、预算、参会者求助 | 无信号询问与求助链跑通 |
| D8–10 | N05/N06；分层处理、人工验收、结果冻结 | 单任务结果与错误定位跑通 |
| D10 | N09；Outbox 与 C1 崩溃恢复 | 恢复后零重复外发 |
| D11 | N11；四个核心行为模板 | 主场景行为覆盖完成 |
| D12 | N12；GATE、SIGNAL 与错误报告 | 指标可重算且证据可追溯 |
| D13 | N13/N15；角色页面、团队工期、报告/Memory | UI 与 API projection 一致 |
| D14–15 | 聚合、E2E、修复、README、演示和缓冲 | P0 通过条件全部满足 |

止损规则：

1. D5 未完成：抽取改用冻结 fixture，保留负责人确认，不砍多同事链路。
2. D9 未完成：减少交付字段数量，不砍版本与 lineage。
3. D12 未完成：报告先输出 JSON；不砍 5 个 GATE，SIGNAL 可先不做图表。
4. 任何延期不得通过删除最小权限、版本/结果防护、Outbox 或多同事 actor 保住工期。

## 10. 交付物

- 可运行的模块化单体 repo；
- 一份通用团队周会场景；
- 1 名会议负责人、3 名参会执行人的脚本角色与 4 个核心行为；
- 角色页面、团队工期、FINAL_RELEASE 与分层验收摘要；
- 一次外发崩溃恢复演示；
- `make eval` 或等价单命令运行 P0 主场景并生成 JSON 报告；
- README 与演示录屏。

## 11. 主要风险

| 风险 | 缓解 |
|---|---|
| 抽取不稳定拖慢主链 | P0 允许冻结 fixture，但必须保留本人确认环节 |
| 外部数据下载或清洗拖慢主链 | 优先参考 AliMeeting4MUG 行动项句；只选少量样本并补最小字段标注，访问超过 1 小时即使用项目自建 fixture，不阻塞 P0 |
| 多同事状态交叉造成重复动作 | 单事件循环、领域状态唯一权威、稳定 effect_id |
| 模拟器复杂度膨胀 | P0 脚本行为＋模板话术；LLM 话术列 P2 |
| 版本与终稿状态不一致 | 不可变版本、人工验收后的 current_valid_version_id、AcceptedTaskResult 与字段 lineage |
| UI 占用主链时间 | 先保证 API 与 JSON 报告，再做最小页面 |
| 评测重新学术化 | GATE 只判关键正确性，SIGNAL 只做轻量解释；恢复研究范围必须新增 ADR |

## 12. 后续方向

P1/P2 由 `12-mvp-priority-profile.md` 管理，包括更多行为、更多故障场景、真实 IM、多 Episode 和多任务评测契约。后续扩展必须增加实现宽度，不能改变办公协作主线或把同事模拟器误解为多 Agent 架构。
