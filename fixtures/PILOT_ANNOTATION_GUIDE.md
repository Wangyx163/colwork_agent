# 产品口径候选标注规范 v1.0（5 场先导）

## 0. 这份标注回答什么

AMC-A 说系统在 15 场里产生了 **1,181 条假阳性**。这个数字**无法回答下一步该做什么**——
因为 AMC-A 只认「任务描述 + 时间框架 + 负责人」同句的句子，而我们的产品故意抽得更宽。

那 1,181 条里可能是三种完全不同的东西，对应三种完全不同的修法：

| 如果大头是 | 那么该做 |
|---|---|
| 产品口径下合法、只是 AMC-A 不认 | **什么都不用改**，改的是报数口径 |
| 同一件事被拆成多条 | **语义归并**，不是重排 |
| 真噪音（寒暄、讨论、背景） | **判别式重排或前置过滤** |

**这份标注就是为了把这三块分开。** 在标完之前，任何关于「投重排还是投聚类」的讨论都是猜。

标完之后能算出四个数：

1. AMC-A 假阳性里，有多少其实是产品合法内容
2. 一场会的 hint 能归并成多少个**独立事项**
3. 每场有多少个**独立错误**（而不是多少句话）
4. 每场最多展示 10 张复核卡的预算下，产品任务召回还剩多少

---

## 1. 三条纪律（先看这个）

**① 不要去看 AMC-A 金标。** 它不在标注表里，是故意的。你要标的是「作为会议负责人，我希望看到什么」，
不是「猜 AMC-A 会怎么标」。

**② 不要去看系统把它路由成了 draft 还是 hint。** 也不在表里，也是故意的。
系统的判断在 `candidates.json` 里，标完之后按 `candidate_id` join 回来。
**两个独立判断才能做混淆矩阵；先看一眼再标，就只是给系统的判断盖章。**

**③ 按 anchor 顺序从上往下标，不要跳。** 表已经按逐字稿顺序排好了。
判断「这条和上一条是不是同一件事」在顺序阅读时几乎是免费的，跳着标就得回头翻。

## 2. 标什么：`label` 三选一

按这个顺序问，第一个成立的就是答案：

### HIDE —— 完全不值得出现

出现在复核界面上纯属浪费负责人时间。包括：

> 寒暄、口头禅、转写噪音（「呃，你觉得就是……」）
> 纯背景陈述（「今年我们公司要组织员工出去游玩」）
> 惯例流程描述（「北方一般六七点前要把女方接出来」）
> 会中已完成的动作（「我现在就把文档发群里」，且当场发了）
> 第三方的事（「供应商说下周发货」）

### DRAFT —— 负责人希望直接看到的任务草稿

会议结束后**确实有一件事需要某个人去做**，而且候选已经把这件事说清楚到
「负责人扫一眼就能决定派给谁」的程度。

不要求句内有负责人，不要求句内有时间——**那两样缺了是交给负责人补的，不是判错的理由。**

### HINT —— 信息不足，但值得提醒

有行动的苗头，但候选本身还不足以形成一张任务卡。典型：

> 讨论中出现的倾向，但没拍板（「这块儿我们后面也可以看看」）
> 条件句（「如果预算下来了就把设备买了」）
> 只说了一半（「那个事你跟进一下」——什么事不明）
> 需要看上下文才能确定是不是任务

**判断口诀**：
> 「会议结束后有没有一件事还需要某个人去做？」
> 没有 → HIDE。
> 有，且这张卡片能让负责人直接决策 → DRAFT。
> 有，但这张卡片还不够 → HINT。

## 3. `cluster`：同一件事填同一个号

**一场会内**从 `c1` 开始编号，同一件事的所有候选填同一个 cluster。只出现一次的事项也要给号。

```
rc_aaa   完成街采视频拍摄        c1
rc_bbb   周四开始拍街采          c1     ← 同一件事，不同句子
rc_ccc   街采视频周末剪出来      c1     ← 同一件事的另一个侧面
rc_ddd   确认线下聚会时间        c2
```

**这一列是整份标注里最值钱的东西。** 「52 条 hint」和「52 个错误」是完全不同的产品问题：
前者靠归并解决，后者靠重排解决。**没有 cluster，这两者无法区分。**

规则：
- 跨 cluster 不复用编号；换一场会重新从 `c1` 开始
- 拿不准是不是同一件事 → 判成**不同** cluster，并在 `note` 写一句
- 引文完全相同的两条候选，一定是同一个 cluster（这种在数据里已经出现了）

## 4. `reason`：七选一

| 代码 | 含义 |
|---|---|
| `REAL` | 真实行动项：会后确实有人要做一件事 |
| `WEAK` | 弱决策：倾向已出现但没拍板 |
| `COND` | 条件句/假设：「如果…就…」，前提尚未成立 |
| `DISC` | 讨论/发散：在聊这件事，但没有形成决定 |
| `BG` | 背景事实、既定前提、惯例描述 |
| `DUP` | 与本场另一条候选是同一件事（**必须同时填 cluster**） |
| `CHAT` | 寒暄、无关内容、转写噪音 |

**为什么把 `CHAT` 从 `DISC` 里单拆出来**：如果错误大头是 `CHAT`，修法是一个廉价的前置过滤器；
如果大头是 `DISC`，那是真正的语义判别问题，得上重排。**两者成本差一个数量级，混在一起就看不出该修哪个。**

`reason` 记的是**你的**理由。系统自己也给每条候选记了 `reason_code`（`ACTION_NOT_ANCHORED`、
`QUESTION_OR_HYPOTHETICAL_UNCONFIRMED` 等 12 类），标完之后两边交叉制表——
**那张表直接告诉你哪条路由规则判错了**，比一个总的准确率有用得多。

## 5. `missed.tsv`：全文漏项

标完候选后，**通读一遍 `transcript.txt`**，把「负责人希望看到、但系统一条候选都没产生」的事项记下来。

| 列 | 填什么 |
|---|---|
| `anchor` | 逐字稿里的行号（`transcript.txt` 行首方括号里那个数） |
| `timestamp` | 该行的时间戳 |
| `what_should_happen` | 会后要发生什么事 |
| `why_wanted` | 为什么负责人会想看到它 |

这一列决定第 4 个数能不能算。**没有漏项登记，「10 张卡覆盖了多少」的分母就不存在。**

## 6. 工作量与顺序

| 会议 | 候选 | 逐字稿单元 | 建议顺序 |
|---|---:|---:|---|
| M3179 | 57 | 227 | ① 最短，先拿它校准手感 |
| M3246 | 53 | 299 | ② 零金标却出 24 个 draft，冲突最尖锐 |
| M2857 | 33 | 461 | ③ 同为零金标但只出 2 个 draft，做 M3246 的对照 |
| M3284 | 57 | 365 | ④ |
| M2869 | 97 | 504 | ⑤ 最大，放最后 |
| **合计** | **297** | **1,856** | |

**标完 M3179 就先跑一次计分**，确认口径和脚本都对，再往下做。
一次把 297 条标完再发现标错了，返工成本是五倍。

预计：候选判定 20–25 秒/条 ≈ 2 小时；通读找漏项 ≈ 2 小时。**总计约 4 小时。**

## 7. 标完怎么验

```powershell
$env:PYTHONPATH = "src"
python scripts/score_annotation_pilot.py --pilot var\annotation\pilot5
```

校验器会检查：`label` 与 `reason` 是否合法、`DUP` 是否都填了 cluster、
`candidate_id` 是否被改动过、漏项的 anchor 是否真实存在。

**全绿之后才看结论数字。** 有校验错时算出来的四个数是错的。

---

## 8. 这份标注不做的事

- **不会**按系统的路由结果反过来调整标签——那是给系统的判断盖章
- **不会**把「标了但系统没抽到」的漏项从分母里筛掉——那是挑对自己有利的算法
- **不会**声称这 5 场能代表整个语料。5 场是**诊断**样本，用来决定下一步投哪里；
  最终报数仍然只能用冻结的 held-out
